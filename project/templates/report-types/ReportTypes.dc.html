Report types

A report type decides what a report is allowed to contain before anyone opens the builder. Get them right and people answer their own questions. Get them wrong and they export to a spreadsheet — quietly, and forever.

The one decision that catches everyone
When you join a second object you choose between "each A must have at least one B" and "A may or may not have B". Nobody reads that sentence carefully, and it silently removes rows.
Accounts with Opportunities hides every account that has none. So the question "which accounts have we never pitched?" cannot be answered by that report type at all — you need with or without, then filter where the opportunity is blank.
Creating
Build a custom one. Always. Salesforce ships a standard type for every object and they look like a shortcut — but you cannot control which fields they expose, and custom fields on related objects are often unreachable.
Start from the question, not the schema. Whoever asked wants one thing counted — the primary object is usually the thing being counted.
You get four objects. A primary plus three related. If you need a fifth, the question is really two reports.
Prove it before you announce it. Build one report on the new type and check the row count against a number you already trust. A join that quietly drops rows looks perfectly normal.
Managing — this is adoption
The name is the interface. It is the first thing a person sees when they click New Report. Write it as the question it answers, not as the objects it joins.
Fill in the description. It shows in that picker and it is the cheapest support you will ever write.
Fewer, better. Forty report types is a wall people walk away from. Retire the ones nobody has used in a year.
Category is navigation. Name categories for teams and put your custom types there. People pick the first thing that looks like their work, so crowd the standard types out.
Test the name on a person. Ask whoever requested it to find it without your help. If they cannot, the name is wrong — not them.
Maintaining
Add a field, then add it again. A new custom field does not appear in an existing custom report type until someone puts it there. Standard types do pick up new fields on the primary object by themselves — the one thing they do better, and no compensation for the related-object fields they will never reach.
In Development hides it. A report type left in that state is invisible to everyone but admins — a common reason a colleague cannot find what you just built.
Deleting one breaks reports. Every report built on it goes with it. Check before you tidy.
Revisit them each release. Salesforce has been changing reporting steadily, and a limitation you built a workaround for may now be handled natively.
Why this is the adoption lever
When someone says reporting in Salesforce is hard, they almost never mean the builder. They mean they could not find a starting point that had their fields in it, so they asked you instead — and next time they will not ask, they will export.
A dozen well-named report types with real descriptions turns that around more reliably than any training. Pair it with one folder rule — only admins save to public folders, everyone else drafts privately — and reporting stays usable a year from now.
