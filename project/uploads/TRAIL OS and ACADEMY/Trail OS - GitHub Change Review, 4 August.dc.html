What landed well

Worth saying first, because the rest of this is problems.

Enforcement is built exactly as designed

Default-deny with a five-entry public list. Authorisation checks the group set, not the derived tier, so two groups keep both grants. The 401 and 403 responses are distinguishable and each carries the right next step. The superadmin whitelist keeps the operator account working. This is the design landed faithfully.

The throttling lesson was generalised

Per-object timeouts, retries, and a rule that a rate-limited or timed-out probe becomes undetermined and never missing. That principle has now been applied across the whole preflight rather than only where it first bit.

Two more schema mismatches caught

The unnamespaced programme engagement object was corrected to its real namespaced name, and a training plan object confirmed absent and removed. Both are the same class of bug as the interaction log, found before they cost anything.

Per-user Salesforce is done

Full authorisation-code flow with PKCE, state validation, silent token refresh, replay protection on the callback, and per-user cache flushing so one person never sees another's cached data. That was a backlog item and it is closed.

DEFECT 1 · MOST SERIOUS

Quest submission always fails, and tells the learner it succeeded

The submission route writes three fields to the quest submission object. Checked against production:

Learner__c — does not exist on this object
Assignment__c — required, and not supplied
Submission_Text__c — exists, and the learner's answer is not written to it

So the insert fails twice over. The helper returns null rather than throwing, the route carries on, and the learner receives success, encouraging feedback from Penny, and a points total. Nothing is recorded. Their written answer goes to Gemini for feedback and is then discarded, even though there is a field waiting for it.

This is the interaction-log bug again, one step worse. That one failed silently; this one reports success. The lesson in the contributor pack — validate written values against the real schema, because mocked tests prove intent rather than conformance — was written two days ago and this shipped anyway.

DEFECT 2

The assignments list queries the wrong object, on two fields that do not exist

The learner dashboard asks the course module activity object for records where the learner matches and a due date falls this week. That object has neither a learner field nor a due date field — it is the curriculum catalogue, describing activities per module, not per person.

The per-learner records live elsewhere: there is a course enrolment object and a course activity completion object, both already in the org, and those are what a learner's assignment list should be built from.

The query fails, the error is caught and turned into an empty array, and the dashboard shows a learner with no assignments — indistinguishable from a learner who genuinely has none.

DEFECT 3

The approval gate you ruled on yesterday is not enforced on the write

You ruled that approving a prompt template requires Penny Admin, and I noted it should be enforced on the write rather than hidden in the interface. On the template routes, only the bulk seed carries an admin check. Create and update carry none — so any signed-in staff member can set a template's status to approved by calling the endpoint directly.

The two-person review rule added in this release has the same shape: the submitter is prevented from approving their own template by the panel that renders the button, not by the route that saves the record. Both are good controls in the wrong layer.

DEFECT 4

A governance gate already in the schema is being bypassed

The course module activity object carries a Quest_Eligible__c flag, and its help text is explicit: only activities where this is true may be used as source material for quest generation by Penny. Someone made a deliberate decision that quests come from approved curriculum.

The daily quest route ignores it entirely. It asks Claude to invent a quest from the learner's trail and phase. The quest submission object's required link to a real activity points the same way — the model expects quests to be tied to curriculum, and the implementation generates them from nothing.

That is a product decision rather than a typo, so it needs your call rather than a fix. But as built, an admin control that exists in the org has no effect.

Three things that need a decision

Not defects. Choices that were made implicitly and should be made deliberately.

Resolved — a learner Google group will gate the learner surface

Settled 4 August. Learner access will be granted through a dedicated Google group, the same mechanism already driving staff access — so learner identity comes from group membership rather than from the presence of a Contact record. The Contact lookup stays, but as the way to find someone's record, not as the test of whether they belong.

That also settles the question the learner read model was waiting on, and it keeps one mechanism for both surfaces rather than two. Worth adding the new group to the staff-group constants as a learner grant when it is created, so the set stays the single place access is defined.

Resolved — quest generation moved to Gemini

Settled 4 August. Penny is one model again, so cost, rate limits and failure modes are uniform across her features. The Anthropic integration stays in place for future use rather than being removed.

One thing to carry: a retained-but-unused integration should still appear in the readiness table, marked as available rather than live. An integration nobody has recorded is the kind of thing that surprises someone during a security review.

The points object is a ledger, used as a counter

The gamification object has fields for who awarded the points, why, a note, and a sprint number — the shape of an award history. The learner code keeps a single row per person and adds to a running total, so every award overwrites the last and the audit trail never accumulates. Both models are reasonable; only one matches the schema.

Correction to my own work

The F-05-05 design was wrong on its central premise

I wrote that prompt templates live in a source file and nothing reads them at request time. They have been database-backed since mid-July, with full create, update and seed routes, a live editing panel, and an auto-seed on first load. I searched the studio page rather than reading the release history, and got it wrong.

What that changes: the sub-feature for making the studio read and write real records is already done. And moving templates to Salesforce — which you agreed to on my recommendation — is now a migration away from a working implementation rather than a first build.

The argument for Salesforce still holds: it keeps behaviour-governing content out of the telemetry store and gives you platform-level audit and permissions. But it is no longer free, so it is worth re-deciding rather than inheriting. The genuinely open work is unchanged either way — the templates still assert their own identity, and nothing yet feeds them to the layer assembler.

What I would do next

1

Stop the learner surface reporting false success

Whatever else happens, a submission that fails must not return success. That is a small change and it is the difference between a feature that is incomplete and one that misleads the person using it.

2

Add a schema conformance check to the test suite

Three write bugs of the same species in three days is a pattern, not bad luck. One test that reads the real object description and asserts every field the code writes actually exists would have caught all three, and would catch the next one for free.

3

Move the two approval controls onto the routes

Admin check on template create and update, and the self-approval rule enforced where the record is saved. Small, and it is the ruling you already made.

4

Decide who counts as a learner, then enforce it

Programme engagement is the obvious test, and it is the same question the learner read model has been blocked on. Answering it once unblocks both.
