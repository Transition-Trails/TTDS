What the connector does well

Worth saying plainly, because the rest of this document is gaps. The validation endpoint is the most carefully written integration code in the repository.

Auth is not hand-rolled

It goes through the Replit connector proxy, so there are no Salesforce credentials in the codebase and no token refresh logic to get wrong. That is the right choice and it removes a whole class of security risk.

Identity check degrades gracefully

If the Chatter identity endpoint is unavailable, it falls back to the limits endpoint and reports remaining daily API calls instead. Two ways to prove the connection is alive, and the fallback is arguably more useful than the primary.

Package detection is real

It probes eight Program Management objects in parallel, records which are accessible and their row counts, sorts accessible first, and reports a fraction rather than a boolean. That is a genuinely informative readiness signal.

The org URL is resolved, not guessed

Rather than assembling a Lightning URL from the instance name — which breaks on My Domain and after migrations — it reads the real base URL from the OAuth userinfo response. A small thing that someone thought about properly.

What it cannot do

5 findings

Two of these block whole features elsewhere in the platform.

SF-01

Blocker

The connector is read-only. There are no write paths at all.

All four endpoints are GET, and every Salesforce call is a SOQL query. Nothing creates or updates a record. That single fact blocks a long list of features that appear to be UI problems and are not:

Penny cannot persist an interaction. A quest cannot be assigned. A submission cannot be recorded. A career review cannot be saved. A weekly report cannot be stored. Points and badges cannot be awarded. Every one of those is waiting on the same missing capability.

Recommendation — one generic authenticated write helper, then the specific endpoints on top of it. This is the highest-leverage piece of work in the whole connector: it unblocks more features than anything else on any list I have seen today.

SF-02

Blocker

No custom object is queried or validated

The validation endpoint proves Contact, Account, NPSP and the eight Program Management objects. It never names a single object you built.

To be clear about the cause, because it changes the size of the job: this is not a connection problem. The objects are deployed, the trail configs are populated, and the connected user can read them. The connector proxy would return them today if a query asked. Nothing does.

Two consequences. Trail OS reads none of your own data, which is why twenty of its thirty-five data files are still illustrative. And the readiness page cannot tell you whether the objects deployed correctly in any environment — the place that would tell you does not look.

SF-03

Defect

The Cases list almost certainly sorts backwards

The open-cases query orders by Priority DESC. Salesforce sorts picklists by their defined order, not alphabetically — and the standard Case priority order is High, Medium, Low. Descending therefore returns Low first, so the twenty-five cases shown are the least urgent ones and high-priority cases can fall off the end entirely.

Recommendation — worth checking against your actual picklist order before changing, since a customised order changes the answer. But the intent is clearly "most urgent first", and as written it is unlikely to be doing that.

Tracked as a defect — agreed 3 August. Carried below as F-05-12 and to be raised as a defect record in Salesforce rather than carried in this document.

SF-04

Ruling

A failure and a zero look identical

Every operations query is wrapped in a helper that catches any error and returns null. A permissions problem, a missing field, a malformed query and a genuinely empty result all arrive at the interface the same way. Worse, the status filters use hardcoded picklist values — Active, Planning, High — so if your org uses different values the query succeeds and returns zero, which is not even null.

A dashboard showing "0 active programmes" when the real answer is "the picklist value is spelled differently" is worse than an error, because it looks like information.

Recommendation — return the error alongside the value rather than swallowing it, and read the picklist values from the org rather than hardcoding them. The design system now has a critical state and a neutral state; use them to show the difference between broken and empty.

Agreed — 3 August. Carried below as F-05-11. Reading picklist values from the org also removes the hardcoded 'Active', 'Planning' and 'High' assumptions, so this closes the silent-zero problem at the same time.

SF-05

Cleanup

Environment details are in the source, and results are silently truncated

The connector identifier is written into a code comment, which will be wrong the moment there is a second environment. The API version is pinned inline in the request path rather than configured in one place. Queries cap at twenty-five cases and fifty programmes with no pagination and no indication that more exist. And the cache is in-memory per instance, so it resets on restart and will diverge if the app ever runs more than once.

Recommendation — all minor individually, all cheap now. The truncation is the one I would fix first: a list that quietly stops at twenty-five is a wrong answer presented confidently.

Agreed — 3 August. Split across F-05-12 (truncation, with the priority sort) and F-05-13 (environment config and shared cache). Moving the connector identifier and API version into configuration is what makes a staging environment possible, so it is worth doing before promotion work starts.
