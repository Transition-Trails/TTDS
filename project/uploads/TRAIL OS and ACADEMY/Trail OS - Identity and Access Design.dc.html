Identity and access · design

One sign-in, three grants

What you described is the right architecture and it is achievable. One clarification makes the whole design fall into place: Google SSO can authenticate the person once, but it cannot by itself give Trail OS permission to act in Salesforce or Slack. Those need their own grants.

The good news is that if Salesforce and Slack already sign in through Google, those grants cost the user a consent click each, once, and never a password. It feels like one login because it is one identity.

THE THING TO KNOW FIRST

Trail OS has no per-user login today

The Google OAuth route in the codebase looks like a login flow but is not one. It is a one-off admin wizard: an administrator runs it, Google returns a refresh token, and the wizard tells you to paste that token into Replit Secrets. Trail OS then uses that single token for Drive, Calendar and Gmail — acting as one account for everyone, forever.

That is a reasonable way to give an application service access. It is not sign-in. It stores nothing per person, it has no session, and it is explicitly memory-only with a ten-minute expiry.

Clerk provides the actual login and is mounted across the API — but it attaches identity without enforcing it, and nothing connects it to your Google Groups. So the honest summary is: the plumbing for what you want mostly exists, but it is wired for service access rather than for people.

Why three grants, not one

This is the one technical constraint that shapes everything else, so it is worth being precise about.

A Google sign-in proves who someone is. It produces a token that says "this is angela@transitiontrails.org, verified by Google". Salesforce will not accept that token as authority to read records, and Slack will not accept it as authority to post — each system issues its own tokens and only trusts its own.

What Google SSO does do is make each of those grants nearly invisible. If Salesforce and Slack use Google as their identity provider, the user is already signed in when they arrive — they see a consent screen, click once, and never type a password. Consent is remembered, so it happens on first use and effectively never again.

The flow

What a person actually experiences, and what happens behind each step.

1

Sign in with Google

One button. Restricted to the transitiontrails.org domain so no personal account can reach Trail OS.

The OAuth code already in the repository does most of this — it needs a per-user session instead of a token-display page.

2

Their groups become their access

At login, Trail OS asks the Directory API which groups this person belongs to, and that determines what they can see. No separate permissions table to maintain — you manage access in the Google Admin console, where you already manage everything else.

The Directory call already works; today it lists members for an admin screen. The same call with a user key answers the reverse question.

3

Connect Salesforce — one click, once

Immediately after login, redirect to Salesforce. Because they are already signed in with Google, they see a consent screen and nothing else. Their refresh token is stored against their account so it never happens again.

Trail OS then reads Salesforce as them — their sharing rules and field-level security apply automatically, with no permission logic to write.

4

Slack when they first need it

Not everyone acts in Slack from Trail OS, so asking at login adds a step most people do not need. Request it at the point of use instead — the first time someone sends a message or assigns a quest.

The decision this forces

Some things must act as the user. Others cannot.

If Trail OS reads Salesforce as the signed-in person, permissions work beautifully — a coach sees their learners, a staff member sees what their profile allows, and you never write authorisation code. That is the right model for anything on screen.

But Penny writes an interaction log after the reply is sent, the nightly sync runs when nobody is signed in, and a weekly report is generated on a schedule. None of those have a user. They need the dedicated integration user you already approved.

So the answer is both, deliberately split: user context for anything a person is looking at, system context for background work. That is a clean rule, and it means the integration user feature is not superseded by this design — its scope narrows to background operations only, which is also a smaller and safer permission set.

Access levels, and the multiple-groups problem

You raised this earlier and it lands here. A person can hold Penny Admin and Platform Admin at once, and today's model cannot express that — access is a single rung on a four-step ladder, so a second group has nowhere to go.

Group-derived access fixes this naturally, provided the groups are read as a set rather than resolved to a single tier. Each group grants something; a person holds everything their groups grant. Two groups mean two grants, not a contest over which one wins.

Access from Google Group membership

At login, resolve the person's groups through the Directory API and hold them as a set of grants on the session — never collapsed to a single tier. Cache with a short expiry so a group change takes effect within minutes. Acceptance: someone in two groups holds both sets of permissions; removing someone from a group removes their access without a code change or a restart; someone in no Trail OS group cannot sign in.

Enforce access on every route

Grants currently describe access without restricting it — the prototype default is Super Admin and there are no route-level checks. Add enforcement at the API, not only in the navigation. Acceptance: a request for something the session does not grant is refused regardless of how it was made; the prototype default is removed; an unauthenticated request to any data route is refused. This is what makes the previous two features real rather than cosmetic.

One thing left to confirm

Confirmed 3 August — Salesforce uses Google as its SAML identity provider. So the Salesforce grant is a single consent screen with no password, and it happens once. Onboarding is genuinely "sign in with Google, approve Salesforce, done". This also means a person's Salesforce access is already governed by their Google account, so disabling someone in Google Workspace closes both doors at once.

Clerk or Google directly? Clerk is already mounted and can sit in front of Google, giving you session management for free. Going direct removes a dependency and a moving part. Either is defensible; running both is not, and today you effectively have two half-wired identity systems. This is the one call I would want settled before any code is written.

One sequencing note: the integration user work stands, but its scope narrows to background operations. Worth updating that feature before it is built, so it is not given permissions that per-user access will cover.
