The same identifiers mean different things

The documentation is far more complete than I expected. There is a product vision with twelve capabilities and twenty-four epics, two workbooks carrying fifty-six features with acceptance criteria and readiness gates, a full PRD, a measurement system, a user guide, and four implementation runbooks. The good news: the Product Vision is the most recent and most complete of the three, and reading it answers two of the rulings I was about to ask you for.

The two plans underneath

Beneath the numbering, the two document sets genuinely describe different work. Both are real. They share a team and almost nothing else.

Plan A — Run the organisation

Product Vision + the two Features workbooks

Eleven epics and fifty-six features — twenty-nine in the first workbook, twenty-seven in the second, which also cross-references two of the first's as dependencies. Salesforce-centric and operational: clean up thirty-six Program Engagement records, define stage progression, build a coach record type and certification checklist, a Session Log object, Google Classroom enrolment sync, commerce and revenue flow, marketing campaigns, analytics and funder reporting.

Governed by readiness gates — twenty in the first workbook alone, of which two are complete and eighteen are Not Started, and nothing executes until they are confirmed. The second workbook carries no gate table at all.

What it is really about: making Salesforce able to run the programmes.

Plan B — Finish the platform

Trail OS Phase 2 PRD

Fifteen features across five sprints. Replit and Gemini centric: wire Ask Penny and Test Penny to live Gemini, replace prototype fixtures with Salesforce queries, deliver quests and career review, build RAG over knowledge sources, generate weekly intelligence reports, add fifty tests, and retire the Penny POC.

Governed by a prerequisite checklist and a risk register, with sprint sequencing and dependencies.

What it is really about: making the Replit app stop being a prototype.

Neither plan contains the other's work. Plan A never mentions Penny's AI wiring, RAG, or POC retirement. Plan B never mentions program engagement cleanup, coach infrastructure, commerce, marketing or analytics. Both are needed, and the same three people deliver both. Until one document sequences them together, whoever joins will pick up whichever they were handed and work in a direction the other plan does not expect.

Settle before onboarding anyone

Three documents each tell Hugh what to build first

The PRD — a five-item prerequisite checklist before Sprint 1: resolve the object promotion errors, define the weekly report schema, verify the Gemini key, decide the Agentforce boundary, review the Figma file.

The Features workbooks — twenty readiness gates in the first workbook, and "no stories execute until gates are confirmed". Eighteen are Not Started. On its own terms, almost nothing in Plan A can begin.

The Measurement System — its own section titled "What Hugh Builds First", plus contact fields to add for outcome measurement and a JotForm survey pipeline that appears in no other document.

Each is reasonable alone. Together they are three first weeks. This is the single highest-value thing to fix, because it is the question a new engineer asks on day one and there is currently no answer — only three answers.

RC-01

Answered

Retiring the POC removes the learner experience — but the Vision says where it goes

Penny POC v2 is not a prototype. Twelve learner screens, four coach screens, a real database, a Slack bot, eleven hundred tests. F-404 switches it off, and nothing in the PRD rebuilds those sixteen screens — quests move to Slack direct message, career review to an admin tab, mobile deferred to Phase 3.

The Product Vision resolves it. E-02, Penny — Learner Coach (Portal): "Penny inside the Experience Cloud learner portal." Phase 1, In Progress. Alongside it, E-01 puts Penny on the Commerce Cloud storefront for prospective learners, E-03 covers Slack, and E-04 makes her a coach coordinator. The learner surface is the Experience Cloud portal — not Slack-only, and not Trail OS.

What still needs deciding — this contradicts two things you have said recently. The PRD's non-goals call a learner portal "a separate product", and you told me coach and learner views belong inside Trail OS gated by Google group. The Vision says Experience Cloud. Three answers, and this one determines where the surface designs get drawn. It is the only ruling I need before I can start them.

RC-02

Answered

The prompt architecture is seven layers — the PRD is the outlier

The PRD specifies five layers and names them. The Six-Pager, the Agentforce setup guide, and now the Product Vision all say seven — the Vision states it explicitly in the E-02 description. Three documents to one, and the three include the newest.

One thing to clean up: the Agentforce guide numbers its layers one, two, three, five, six and seven, skipping four. Layer four is almost certainly the knowledge retrieval layer that the PRD calls L4 — meaning the seven-layer scheme is the five-layer one with the dynamic context layers split out, and nobody wrote the missing number back in.

Action — correct the PRD to seven and publish one canonical layer list with all seven numbered and named. This is the first thing built in Sprint 1, so it wants settling this week.

RC-03

Blocker

The Salesforce object list does not agree between its own two documents

The PRD lists eight objects under the build work item plus a ninth to create before Sprint 3. The Penny Salesforce Build Requirements document opens with three objects as its top priorities — a capability object, a prompt object and a session log — none of which appear in the PRD's list. It also carries thirteen seed capability records, which is a genuine asset and referenced nowhere else.

Recommendation — one object inventory, owned by the data model workbook, with the build work item tracking against it. Right now the true object count is unknowable from the documents.

What I propose for the new documents

You asked for brand new Epics, Features and design documents. Having read what exists, I would not start from scratch — the Product Vision already has capabilities, epics and a roadmap, and the workbooks already have fifty-six features with acceptance criteria. Rewriting that would lose work and create a fifth numbering scheme.

1

One epic map, on the Vision's numbering

Adopt the Product Vision's twenty-four epics and twelve capabilities as the single scheme. Remap the workbooks' fifty-six features onto those IDs — the features are good, only their epic labels are wrong. Fold the PRD's fifteen features in as well. One identifier system, one backlog, no orphans, and a written note that the old workbook epic numbers are retired so nobody reuses them.

2

One sequence — the answer to "what first"

A single ordered path through the readiness gates, the PRD prerequisites and the measurement build, with what blocks what. This is the document a new person reads first, and it is the one that does not exist yet in any form.

3

Design documents for the surfaces, not the whole platform

Genuinely new work, once RC-01 is settled: the coach surface, the learner surface, and the shared states the prototype has never needed. Everything else already has a document.
